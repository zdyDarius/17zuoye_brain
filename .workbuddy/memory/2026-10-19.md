## 修复：chapter_name / content 超 VARCHAR 长度导致分块静默丢失（P0）

- 现象：重导文档报 `MilvusException code=1100`，`chapter_name` length 187/200 > 128，`content` length 4460 > 4096；`logs/app_20261019.log` 中共 48 次 chapter_name + 1 次 content
- **根因 1（设计缺陷）**：分块参数按**字符**计（`CHUNK_MAX_SIZE=3000`），Milvus `VARCHAR max_length` 按 **UTF-8 字节**计（中文 3B/字）→ 3000 汉字 = 9000B，必然超过原 4096B；约 1365 汉字以上的块全失败
- **根因 2（MinerU 误判）**：MinerU 把整段正文导成 `#` 一级标题（如 `# 词表（Vocabulary）是由语料库构建出的…`，200B）→ 进入 `chapter_stack`；且代码里 level<=2 的标题行**只进栈不进正文**，该段内容被静默吞掉（不只是超长）
- 修复（3 处）：
  1. `node_course_doc_parser.py`：新增 `MAX_HEADING_CHARS=60`；`len(title) > 60` **或** `title.endswith(("。","；"))` → 视为正文（去 `#` 前缀），不 flush、不入栈
  2. `node_import_milvus.py` schema：`edu_course_doc.content` 4096→**16384**、`chapter_name` 128→**256**、`project_name` 128→256
  3. `node_import_milvus.py` 新增 `_clip_varchar()`：按 `_SCALAR_FIELDS` 的 max_length **字节**统一截断（`decode("utf-8","ignore")` 防切断多字节）+ warning，在 `_to_row` 末尾调用，防任何字段再炸
- 效果（对 output/20261019 的 7 份 md 复算）：章名最大 **127B**（原 200B）、正文最大 3878B；Python1.0 **646 → 382 块**（264 个碎块因正文回归而合并）
- **schema 变更需重建 collection**（Milvus 不能改已有 max_length）：已 drop 并按新 schema 重建 `edu_course_doc`，重建前 992 块（5 份讲义）记录在 `/tmp/doc_collection_before_rebuild.json`；**导入服务 :8000 必须重启才加载新代码**

## 新增评估防泄漏机制（eval/check_gt_leakage.py）

- 解决的是「评估设计缺陷」而非「草稿没核对」：出题人看着检索块写问题+答案时，问题/答案/被检索内容三者同源，RAGAS Context Recall 必然虚高
- 脚本指标：`gt_lcs`（ground_truth 与 golden 块最长**连续**公共子串）/ `q_lcs`（query 同理）/ `cov5`（gt 的 5-gram 被块覆盖率）
- 阈值：`gt_lcs>=50` 严重抄袭；`>=30` 或 `cov5>=0.55` 可疑；`>=20` 轻度；其余 OK。**有严重/可疑时退出码 1，可接 CI**
- 用法：`PYTHONPATH=. .venv/bin/python eval/check_gt_leakage.py [dataset.json]`（默认 golden_dataset.json）
- 首轮检测抓出 2 条并修掉：
  - **D03** 把 `threading.Thread(group=None,target=None,...)` 整个签名抄进答案（65 字连续）→ 改为参数语义描述，降到 18 字
  - **D12** 原章节「2.3 RAG」只有 3 块 1164 字符，答案几乎压缩复述整章（cov5=75%）→ 换到 26 块的「2.2 提示词工程」，改问上下文窗口，cov5 降到 54%
- 修后 16 条全部 ≤25 字 / 0 严重 / 0 可疑；残留 20–25 字均为术语与定义句式（如"字符级（Character-Level）"），技术文本不可避免
- **方法论（后续出题照此做）**：
  1. 出题只看章节标题，不看块正文，问题用场景化口语（"改嵌套列表为什么原列表也变" 而非 "浅拷贝和深拷贝的区别"）
  2. ground_truth 由人读原始 docx 写，**不看检索结果**
  3. 章节块数太薄（<5 块）不适合做黄金用例，答案必然贴着原文写
  4. 补 3–5 条「库里没有答案」的负样本，测拒答能力（天然不受同源影响）
  5. 每次改黄金集都跑一次 check_gt_leakage.py
