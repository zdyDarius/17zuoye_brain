> 分析对象：`17zuoye_brain` 教育知识库问答系统（问答服务 `:8001`）

## 2. 端到端时序

### 2.1 非流式（`is_stream=false`）

```
Client                query_service              query_app(graph)            Milvus/Mongo/LLM
  │ POST /query             │                          │                            │
  ├────────────────────────>│                          │                            │
  │                         ├─ 参数校验（空 query → 400）                            │
  │                         ├─ session_id 缺省 → uuid4                              │
  │                         ├─ get_recent_messages(limit=12) ──────────────────────>│ Mongo
  │                         │<──────────────────── 历史（新→旧）─────────────────────┤
  │                         ├─ create_query_default_state(...)                      │
  │                         ├─ query_app.invoke(state) ────────>│                    │
  │                         │                                  ├─ 6 个节点顺序/条件执行 ──>│
  │                         │<──────────── final_state ─────────┤                    │
  │                         ├─ save_chat_message(user)  ───────────────────────────>│ Mongo
  │                         ├─ save_chat_message(assistant, references) ───────────>│ Mongo
  │<── {session_id, answer, references, degraded} ────────────┤                    │
```

关键点：
- 历史**在写入当前提问之前**读取（`:117-121`），避免当前问题污染上下文 —— 正确。
- 图整体异常 → `500 query error`（`:135-137`）；节点内部异常基本被各节点自行 try/except 吞掉，所以 500 很少出现。

### 2.2 流式（`is_stream=true`）

```
Client                    query_service                      后台线程 run_query_graph
  │ POST /query(is_stream)      │                                      │
  ├────────────────────────────>│                                      │
  │                             ├─ create_sse_queue(sid)               │
  │                             ├─ background_tasks.add_task ─────────>│
  │<── {session_id, message} ───┤                                      ├─ create_sse_queue(sid)
  │                                                                    ├─ push(step, {node:start})
  │ GET /stream/{sid}            │                                      ├─ for event in query_app.stream(updates):
  ├────────────────────────────>│                                      │     push(step, {node:<name>})
  │<── event: ready ────────────┤                                      │
  │<── event: step(node=xxx) ───┤<─────────────────────────────────────┤
  │                             │                                      ├─ save_chat_message ×2
  │<── event: final ────────────┤<─────────────────────────────────────┤
  │                             │                                      └─ remove_sse_queue(sid)
```

- **事件契约**（`utils/sse_utils.py:8-15`）：`ready` / `step` / `final` / `error` / `progress` / `delta`。
  实际只用到 `step`、`final`、`error`；`delta`（token 级增量）与 `progress` 定义了但**从未发送** —— 答案是一次性整段返回，不是逐字流式。
- **缓冲回收**：`push_to_session` 给每条事件分配自增 id 并写入重放缓冲（上限 200 条）；任务终态（final / error）后调用 `schedule_session_cleanup`，默认 300s（`SSE_REPLAY_TTL_SECONDS`）后清理该会话的队列/缓冲/id 计数，避免内存随会话数线性增长。清理前会校验期间是否已有新的活跃队列或新事件，避免误清重连窗口。

### 2.3 状态图结构（实测，修复后）

```
__start__ → node_query_rewrite → node_intent_route
                                    ├─(ambiguous)→ node_answer_output
                                    ├─(catalog)  → node_structured_query → node_answer_output
                                    ├─(aggregate)→ node_aggregate ───────→ node_answer_output
                                    └─(content)  → node_semantic_fanout
                                                     ├→ node_search_embedding ─────┐
                                                     ├→ node_search_embedding_hyde ─┼→ node_rrf → node_rerank → node_answer_output
                                                     └→ node_question_filter ───────┘
node_answer_output → __end__
```

- 三路召回从同一个空操作扇出节点并行进入，再用**多源 `add_edge([a,b,c], "node_rrf")`** 让 RRF 等全部上游完成后执行（LangGraph 语义已用最小图验证：0.31s ≈ max(0.3,0.3,0.3)，而非 0.9s）。
- 修复前这两路是孤岛（只有出边、没有入边），永远不会被调度；详见 §10.1。
- 复现方式见 §12。

## 3. 状态字典（`QueryGraphState`）

`processor/query_processor/state.py:8-45`，`total=False`（全部 key 可选）。按「谁写 → 谁读」梳理：

| 字段 | 写入节点 | 读取节点 | 说明 |
|---|---|---|---|
| `session_id` | API | 日志 / SSE 追踪 | 也用于 `node_log` 的 trace_id |
| `original_query` | API | 题型澄清判定、兜底 | 用户原词（如「填空」）以此为准 |
| `rewritten_query` | query_rewrite | **intent_route、structured、aggregate、3 个语义节点、answer_output** | 全链路的"理解 + 检索"依据 |
| `is_stream` | API | — | 仅透传，图内无分支使用 |
| `history` | API（12 条，**旧→新**） | rewrite / intent_route | API 侧已 `reversed()`，节点取尾部即最近 |
| `intent` | intent_route | `route_after_intent`、answer_output | `catalog`/`aggregate`/`content`/`ambiguous` |
| `entities` | intent_route | structured / aggregate / question_filter | 13 个白名单 key + `_invalid_question_type` |
| `route_reason` | intent_route | — | 仅日志/调试 |
| `structured_results` | structured_query | answer_output（context + references） | 扁平列表，每条带 `_collection` |
| `structured_total` | structured_query | — | 真实命中总数（`count(*)` 汇总） |
| `structured_truncated` | structured_query | answer_output（仅拼一句提示） | 任一 plan 超 100 即为 True |
| `aggregate_result` | aggregate | answer_output | `{value, groups?, filter?, course_rows?, entities}` |
| `aggregate_field` | aggregate | — | 白名单校验结果，含 `count` / `course_count` 两个伪字段 |
| `embedding_hits` | search_embedding | rrf | 原查询混合召回 |
| `hyde_hits` | search_embedding_hyde | rrf | HyDE 假设答案召回（已生效） |
| `question_filter_hits` | question_filter | rrf | 实体预过滤召回（已声明并进入融合） |
| `fused_results` | rrf | rerank | RRF 融合序（带 `_rrf_score`） |
| `reranked_results` | rerank | answer_output | Top-5 |
| `search_collections` | intent_route（默认值在 state） | 3 个语义节点 | 默认 4 个集合；含题型/题库实体时收窄为 `["edu_question"]` |
| `answer` | intent_route（反问）/ aggregate（澄清）/ answer_output | API / SSE | 三个节点都可能写，后者会覆盖前者 |
| `references` | answer_output | API / Mongo | 编码级引用 |
| `degraded` | rerank / answer_output | API / SSE | 仅在重排失败、LLM 失败时置 true |
| `error` | structured / aggregate / 3 个语义节点 | **无人读取** | 故障信息在此断链（§6.9） |

> 设计缺口：`question_filter_hits` 缺失不是笔误级别的疏漏，而是**语义通道第三路根本没接入状态机**的直接后果。

## 4. 逐节点详解

### 4.1 `node_query_rewrite` —— 多轮指代消解

`processor/query_processor/nodes/node_query_rewrite.py`

**职责**：把「第一个系列里有几门课」「换成编程题呢」这类依赖上文的问题改写成独立可检索的问题。

**控制逻辑**：

| 条件 | 行为 | 行号 |
|---|---|---|
| `history` 为空 | 原样透传，不调 LLM | `:27-28` |
| 问题不匹配指代词正则 | 原样透传 | `:31-32` |
| 命中指代词 | LLM 改写（历史取 `history[-6:]`，截断前 300 字） | `:36-57` |
| 改写结果为空 / 长度 > 原文 10 倍 | 回退原问题 | `:59-63` |
| 异常 | 回退原问题（`logger.warning`） | `:65-67` |

指代词正则（`:13`）：`它|这|那个|上述|刚才|前面|第一|上一|换个|换成|相关`

**实测效果**（`logs/`）：

```
查询改写：第一个系列里有几门课？ → 通用编程入门班包含哪些课程模块
查询改写：换成编程题呢？ → 有哪些编程题？
```

**问题（均已修复）**：

1. ✅ **历史顺序取反**（P1）。原实现取 `history[-6:]`，而 Mongo 返回的是新→旧，拿到的是**最旧的 3 轮**。已改为在 `query_service` 侧统一 `reversed()` 成正序，节点内 `history[-6:]` 语义恢复正确（最近 3 轮）。
2. ✅ **指代词过宽**（P2）。`相关` 是最常见的普通词（「XX 相关的练习题」），实测出现过「神经网络相关的知识 → 有哪些神经网络相关的课程」的改窄事故。已从正则移除，并补上「这些/这种/这里/第二/第三」等明确指代。
3. ✅ 改写 prompt 已从节点内联抽到 `common/prompt/rewrite.prompt`，并新增「不要扩大或收窄意图」约束。
4. ⚠️ 改写仍只看文本、不看实体，失败不标记，下游无感知（低风险，暂留）。

### 4.2 `node_intent_route` —— 意图分类 + 实体抽取

`processor/query_processor/nodes/node_intent_route.py`（查询链路里最"重"的节点）

**职责**：一次 LLM 结构化输出（`json_mode=True`）同时给出 `intent`、`entities`、`route_reason`，是整个分流的唯一决策点。

**执行步骤**：

| 步骤 | 代码 | 说明 |
|---|---|---|
| ① 拼历史 | `:42-52` | 取 `history[-4:]`（已在 API 侧转正序），每条截 100 字 |
| ② 渲染 prompt | `:55` | `common/prompt/intent_route.prompt`，注入 `{query}`（**改写后**）+ `{history}` |
| ③ 调 LLM | `:52-54` | `get_llm_client(json_mode=True)`，模型 `qwen-flash` |
| ④ 容错解析 | `:57-60` | 正则 `\{[\s\S]*\}` 剥 markdown 代码块后 `json.loads` |
| ⑤ 意图枚举校验 | `:62-64` | 非法值一律降 `ambiguous` |
| ⑥ 实体白名单 | `:67-68` | 只保留 `VALID_ENTITY_KEYS` 的 key，且值非空 |
| ⑦ 题型枚举校验 | `:71-73` | 不在 15 种 → 弹出并记 `_invalid_question_type` |
| ⑧ 自纠偏防护 | `:76-82` | 原文含「填空」但 LLM 改判「完形填空」→ 还原为非法题型 |
| ⑨ 内容型实体瘦身 | `:86-88` | content 意图下丢弃 `course_category/series_name/course_name/target_audience/suitable_grade/learning_goal/course_code` |
| ⑩ 检索集合定向 | `:90-94` | 含 `question_type_cn` 或 `bank_name` → 仅 `edu_question` |
| ⑪ 聚合字段兜底 | `:96-101` | 不在 7 个白名单字段 → 丢弃 |
| ⑫ 序数残留防护 | `:103-108` | 实体值含「第一/第二/这个/那个/它」→ 丢弃（说明改写没生效） |
| ⑬ 系列名代码兜底 | `:110-130` | catalog 且无系列/课程实体 → 拉 300 条系列名做子串匹配补抽 |
| ⑭ 反问分支 | `:135-164` | ambiguous 或非法题型 → 直接产出 `answer`，跳过检索 |

**分流结果**（`main_graph.py:83-107`）：`ambiguous→answer_output`，`catalog→structured_query`，`aggregate→aggregate`，`content→semantic_fanout`（三路并行）。

**优点**（这段代码防御性写得很细）：
- 题型开放集 + 「填空题不存在」的澄清（A3-24）是真实业务坑，处理得当：不是硬映射到「完形填空题」，而是把 15 种枚举回给用户。
- 序数残留防护（⑫）与系列名兜底（⑬）互相补位：LLM 抽错就丢，抽漏就用 Milvus 里的真实系列名反查。

**问题（修复情况）**：

1. ✅ **改写结果没被使用**（P1）。原来读 `state["original_query"]`，改写只在检索侧生效。已改为 `query = state.get("rewritten_query") or original_query` 并用于 prompt；题型澄清的「填空」判定仍以用户原词为准。验证：多轮「第一个系列里有几门课？」→ 改写为「通用编程入门班包含哪些课程模块」→ `intent=catalog`、`entities={series_name: 通用编程入门班}`。
2. ⚠️ **content 意图一律剥掉课程维度实体**（`:86-88`，保留）。好处是避免误过滤缩小召回；代价是「《XX讲义》里讲的状态管理」无法把检索收敛到指定文档（eval D01/D13 章节漂移的成因之一）。属设计取舍，未在本次改动。
3. ✅ 死代码已消除：`bank_code` 已加入 `VALID_ENTITY_KEYS`，`_build_question_filter` 的 `bank_code ==` 分支现在可达。
4. ⚠️ LLM 异常仍一律降 `ambiguous` + 固定反问（`:169-177`）。改进需引入规则兜底，属行为变更，本次未动。
5. ⚠️ 单节点耗时 1.7–4.6s，占全链路 30%+，是首屏延迟主要来源（见 §9）。

### 4.3 `node_structured_query` —— 目录型结构化通道

`processor/query_processor/nodes/node_structured_query.py`

**职责**：catalog 意图下，用 Milvus 标量过滤做「可穷举」的精确查询，不走向量。

**集合路由矩阵**（`:97-111`）：

| 命中实体 | 目标集合 | 过滤表达式 |
|---|---|---|
| `question_code` / `question_type_cn` / `bank_name` | `edu_question` | `question_type=="<en>"` / `bank_name like "%x%"` / `question_code=="x"`，AND 连接 |
| `course_code` / `course_name` | `edu_course_module` | `course_name like` / `course_code ==` / `series_name like` |

**执行与规模保护**（修复后，`:117-175`）：
- 每个 plan 先 `count_rows()`（Milvus `count(*)`）取**真实命中总数**；
- 再 `client.query(limit=100)` 取展示数据，`plan_truncated = plan_total > 100`；
- 多个 plan 的 `total` 累加、`truncated` 取 OR；每条打 `_collection` 标记后合并；
- `count(*)` 失败时回退为「按返回行数估算」，不会让查询整体失败。

**实测**（修复后）：

`like "%...%"` 天然带子串匹配，「通用编程入门班」能命中而不会误命中「通用编程项目班」，符合预期；like 转义已抽为 `escape_like_term`（`utils/escape_milvus_string_utils.py`）。

**问题（修复情况）**：

1. ✅ **总数统计错误**（P2）。原 `limit=101` 时 `len()` 恒 ≤101，`structured_truncated` 用 `any(len(r) > 0 ...) and len(results) >= 100` 会把「多 plan 合并后 ≥100」误判为截断。已改为 `count(*)` 真实总数 + 每 plan 独立截断位 OR 汇总。实测：`target_audience=在校生` → **total=166 / 返回 100 / truncated=True**（原来只能是 101 / 误报）。
