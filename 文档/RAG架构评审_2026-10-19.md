## 二、问题清单

### P0-1 分块 1500 字符 + 零 overlap，与 rerank 512 token 截断叠加

**症状**
- 文档通道 Hit@5 长期在 0.75 ~ 0.94 区间徘徊
- 未命中案例类型高度一致：**概述章节压过具体章节**（D01 / D05 / D13）

**根因（两个问题叠加，同一个病的两面）**

1. **向量侧主题稀释**：`CHUNK_TARGET_SIZE = 1500` 字符对中文偏大。块越大，单向量越接近"该章节的平均语义"；而概述块天然聚合全篇关键词（LangGraph / LangChain / 线性回归），所以在向量空间里对**任何**针对该文档的问题都高度相似 → 概述块系统性胜出。
2. **精排侧信息截断（更隐蔽）**：`FlagReranker` max_length = 512 token。1500 字符的中文块约 1500~2250 token（按 1~1.5 token/字估算），**只有前 1/4 ~ 1/3 参与相关性打分**。块首是【章节前缀】+ 开头段落，真正的答案细节往往在中后段 → rerank 根本没看到答案，只能按"开头这段像不像问题"打分。
3. **零 overlap**：`step_3` 是贪心累积 + `_flush_section` 硬切，段落在边界处完全断开。D15（过拟合：正则化 / Dropout / 早停分散在相邻块）、D16（微调细节分散多块）就是典型的跨块信息断裂。

**修复建议（参数给具体值）**

| 参数 | 当前 | 建议 | 依据 |
|---|---|---|---|
| `CHUNK_TARGET_SIZE` | 1500 | **600–800** | 讲义是知识点型结构化文本，600–800 字符 ≈ 一个完整知识点；同时让 rerank 512 token 能覆盖块的大部分 |
| `CHUNK_MAX_SIZE` | 3000 | **1200** | 上限也应落在 rerank 可见窗口附近，否则超长块的后半段仍不参与精排 |
| overlap | 0 | **80–120 字符** | 实现方式：`_emit_chunk` 时把上一块**最后一个段落**（或末 N 字符）带到下一块开头；不要按字符硬切，会切断句子 |
| 分档 | 单一值 | 讲义 600–800 / 项目文档 800–1000 | 按 `doc_kind` 分两档，项目文档叙事性强、需要更多上下文 |

**代价（必须说清楚）**
- 块数从 426 → 约 900~1000（估算），Milvus 存储与向量化成本翻倍——但绝对量级仍很小（千级），可忽略
- 候选池规模不变 → rerank 耗时不变
- **需要重新导入文档集 + 重跑评估**，是本清单里唯一需要动数据的项

**验证方式**：改完重导，用 v1.1 黄金集跑 `run_retrieval.py`，对比 `doc Hit@5` 与 `MRR`。预期 doc Hit@5 有提升，且"概述章节压过具体章节"类未命中应显著减少。若没有改善，说明根因判断错误，回滚参数即可（切分参数独立，无代码耦合）。

> 附：建议先跑一行诊断确认截断比例，避免基于估算决策：
> ```python
> from transformers import AutoTokenizer
> tok = AutoTokenizer.from_pretrained("<BGE_RERANKER_PATH>")
> print(len(tok.encode("【章节】\n" + chunk_content)))   # 若 > 512，则确认被截断
> ```

### P0-2 RRF 把 4 种异构实体放在同一池里比名次

**症状**
- `edu_course_doc` 的 rank 区间被集合顺序固定在 15~19，单路最高分 `1/76 = 0.01316`
- 低于 `edu_course_series` 第 5 名的 `1/66 = 0.01515`
- 叠加"doc 只有 2 路命中、question 有 3 路"，k=60 又极度奖励"多路共识" → **文档块在 RRF 阶段就结构性落后**（这一点你的文档已识别，`RERANK_INPUT_LIMIT=30` 是补丁）

**根因**
`rank` 是"通道内拼接后的全局位置"，等于把"课程系列排名"和"文档块排名"当成一把尺子。而这两类实体回答的是**不同类型的子问题**，本就不该在同一池里比名次。k=60 的设计假设是"多路共识更可信"，这对异构池不成立——doc 天生少一路。

**修复建议（按性价比排序）**

1. **集合内名次融合**（最正确）：在 `_hybrid_search_collection` 里记录 `_rank_in_collection`，RRF 用集合内名次计算分数。改动约 10 行，每个集合的第一名都从 `1/61` 起算。
2. **补齐 doc 的第三路**（收益最直接）：`node_question_filter` 当前只查 `edu_question`。若实体抽取能识别出文档名 / 项目名，增加一条对 `edu_course_doc.source_file` 的 `like` 过滤检索，让 doc 也有 3 路共识。这比调权重更自然——过滤器本来就该按实体定向。
3. **RRF 加权变体**：`score = Σ w_c / (k + rank)`，给 doc 两路 `w=1.2~1.5`。最省事，但权重需靠评估集调，且换数据集容易失效。
4. **调换集合顺序**：把 `edu_course_doc` 放前面。零成本试错，但会反过来压制题目召回——不推荐作为长期方案。

**代价**：方案 1 需改融合逻辑 + 重跑评估；方案 2 需在意图节点补文档名实体（LLM 抽取可能不稳定，需代码兜底）。

## 附录 A：小块切分如何保证语义完整

> 核心结论：**小块不需要"自己语义完整"，需要"能还原出完整语义"。** 完整性不必由单个块承担——把这件事从"切分时"挪到"检索后"，成本低得多。

### A.1 完整性由三层保障，不由单块承担

| 层 | 机制 | 你当前状态 |
|---|---|---|
| ① 块内自明 | 章节路径前缀 `【A > B】` + 块首主题句 | 前缀已有 ✅ |
| ② 跨块连续 | overlap（按**段落**带入，不按字符） | 缺 ❌ |
| ③ 检索后回填 | 命中块 → 按同章节拉回相邻块 | 缺 ❌，但**数据已具备** |

### A.2 推荐：小块检索 + 章节回填（不必建父子两套索引）

你的 `edu_course_doc` 已经有 `chapter_name` + `chunk_index`，**天然就是父子结构**，不需要额外维护 parent 集合：

```
检索时：小块（600–800 字符）→ 向量不稀释、rerank 512 token 能覆盖全块
回填时：命中块 → 按 (source_file, chapter_name) 反查同章节全部块
        → 按 chunk_index 排序拼接
        → 超预算（如 3000 字符）则退化为「命中块 ±1 邻块」
送给 LLM：完整章节（语义完整、上下文自洽）
```

**收益**：入库粒度小（召回准、精排看得全），生成上下文大（答案完整）。存储零增加、无需重导——只改 `node_answer_output` 的上下文组装。

**边界**：回填只对 `edu_course_doc` 有意义；题目 / 系列 / 模块本身就是原子实体，块即实体，不存在回填问题。

### A.3 不可切分的原子单元（宁超上限也不切）

切分前先标记，落到具体类型：

| 原子单元 | 你当前处理 |
|---|---|
| 代码块（``` 围栏内） | ✅ 已处理（`in_code_block` 开关） |
| Markdown 表格（连续 `|` 行） | ❌ **未处理**——MinerU 输出的 MD 表格会被按行切断，表头与数据行分离后语义归零 |
| 有序步骤列表（连续 `1. 2. 3.`） | ❌ 未处理——操作步骤被拆成两块，每块都是残句 |
| 单个题目（题干 + 选项） | ✅ 由 `node_question_parser` 保证 |

表格和步骤列表是当前最容易被忽略的两个切点。判断规则：**"这一段的语义是否依赖它的上一行/下一行"**——依赖就不能切。

### A.4 overlap 的正确做法

```python
# 错误：按字符切，句子被拦腰截断
overlap_text = prev_chunk[-100:]

# 正确：带上一块最后一个完整段落
carry = prev_paragraphs[-1]         # 段落是天然语义边界
next_buffer = carry + "\n" + ...
```

三条约束：
1. **只带承上内容，不带标题行**——标题重复进多个块会让 rerank 误判"这几块都在讲同一件事"
2. **上限为目标块 15%**（600–800 → 90–120 字符），超过就变成"隐性大块"，白折腾
3. **overlap 不参与 `chunk_index` 计算**，只影响 `content`——否则溯源会错位

### A.5 怎么验证语义完整性（用你已有的评估数据就能诊断）

| 信号组合 | 含义 | 该修什么 |
|---|---|---|
| **Hit@5 高 + RAGAS Context Recall 低** | 块找到了，但信息不全 → **切分把语义切断了** | 加回填 / 加 overlap |
| Hit@5 低 + RAGAS Recall 也低 | 召回或排序没找到正确块 | 与切分无关，动 RRF / 分块参数 |
| Hit@5 高 + Recall 高 | 切分与检索都正常 | — |

**你的 v1.1 数据正好是第一种的样本**：D15（命中排名 2，recall 0.5）、D16（命中排名 1，recall 0.5）——块找对了，但答案信息不完整。这就是"语义完整"问题的量化证据，而不是主观感受。

另一个低成本抽样检查：随机抽 20 个块，只看**块首 100 字**，问自己"这一块在讲什么"。答不上来说明切点选错了（主题句没进块，或块从半句话开始）。
