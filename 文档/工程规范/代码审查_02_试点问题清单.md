## 🔴 P0-1　幂等 upsert 是"先删后插"，插入失败即丢数据

**位置**：`processor/import_processor/nodes/node_import_milvus.py:283-292`

```python
expr = f'{pk_field} == "{pk_value}"'
existing = client.query(collection_name=collection_name, filter=expr, output_fields=["id"])
if existing:
    client.delete(collection_name=collection_name, ids=[e["id"] for e in existing])
    upd_cnt += 1
else:
    ins_cnt += 1
client.insert(collection_name=collection_name, data=[row])
```

**为什么是 Blocker**：`delete` 与 `insert` 之间没有事务。若 `insert` 抛异常（字段超长、字段类型不匹配、网络抖动、Milvus 短暂不可用），`except` 只 `logger.error` 后继续下一条——该业务主键的记录已经被删掉且不会再补回。**下一次重导即永久少一条数据，而任务状态仍是 completed**。

**建议**：
- 首选 `client.upsert(collection_name=collection_name, data=[row])`（`auto_id=False` 且主键显式提供时可用，语义就是本例想要的）；
- 若因版本限制不能用，改为「先 insert 新记录 → 成功后按旧主键 delete 旧记录」；
- 无论哪种，单条失败必须计入 `collection_stats[collection_name]["failed"]` 并让任务状态体现出来。

**验证**：构造一条必定插入失败的记录（如 `content` 超长且关闭截断），重导后比对 `count(*)` 前后是否一致。

## 🔴 P0-2　用户实体直接拼进 Milvus 过滤表达式

**位置**：`processor/query_processor/nodes/node_search_embedding.py:262-264`

```python
if entities.get("bank_name"):
    conds.append(f'bank_name like "%{entities["bank_name"]}%"')
```

**为什么是 Blocker**：`bank_name` 由 LLM 从用户问题中抽取，等同于用户可控输入。问题里带一个 `"` 就会让表达式语法错误（该通道整体失败）；构造得当还能拼出恒真条件，绕过题型/题库过滤，直接污染召回。这属于典型的表达式注入，和 SQL 注入同一类问题。

**建议**：
```python
def _escape_milvus_literal(value: str) -> str:
    """Milvus 表达式字符串字面量转义：先反斜杠再双引号，并限制长度"""
    return value.replace("\\", "\\\\").replace('"', '\\"')[:64]
```
另外不要用 `like "%...%"` 做前缀模糊（对倒排索引不友好）；库名属于有限集合，建议从 `edu_question` 的 `bank_name` 去重值里做精确匹配，匹配不到再退化为不筛。

**验证**：`{"bank_name": 'x" or bank_code != "'}`，观察表达式日志是否被拒或条件失效。

## 🔴 P0-3　服务无鉴权 + CORS 全开，上线即敞口

**位置**：`api/query_service.py:32-37`、`api/file_import_service.py:43-48`、`api/query_service.py:185-212`

```python
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_methods=["*"], allow_headers=["*"])
```

**为什么是 Blocker（有前提）**：当前两服务都绑定 `127.0.0.1`，只在本机可达，**现阶段可接受**。但一旦改成 `0.0.0.0`、放进容器或部署到内网，问题立刻成立：任何人只要知道（甚至猜到）`session_id`，就能 `GET /history/{id}` 读走整段对话、`DELETE /history/{id}` 清空、`POST /upload` 往库里灌任意 `course_doc`。而 `session_id` 由服务端生成、前端明文持有，不具备任何不可猜测性。

**建议**：
- 在 README 与本文档中明确标注「仅限本机使用」的前提，并在代码里加一行断言/启动告警：绑定非 loopback 时 `logger.warning` 提示未鉴权；
- 真正上线前必须做：`allow_origins` 收敛为白名单 + 网关层鉴权 + `session_id` 归属校验；
- 顺带修 `api/query_service.py:148-150`：`detail=f"query error: {e}"` 会把内部异常字符串返回给调用方，改为固定文案 + 日志留全栈。

## 附：这批问题说明了什么

按 00 文档的分级标准，6,536 行业务代码里只找出 3 个 🔴，而且都集中在"边界路径"上——`except` 之后、并发写入、外部输入拼进查询。happy path 写得相当扎实（分块、归一化、RRF、降级矩阵都有注释和实测记录）。

这恰好印证了第 1 节的判断：**问题不在编码水平，在于没有人在看错误路径**。而错误路径恰恰是审查投入产出比最高的地方——00 文档附录里"先看错误路径"那条，就是从这批问题里总结出来的。
