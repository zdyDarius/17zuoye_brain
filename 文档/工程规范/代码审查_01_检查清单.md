# 代码审查检查清单

> 配合 `代码审查_00_标准与流程.md` 使用。
> **作者**：提 PR 前过 A 段（12 条，5 分钟）。
> **审查者**：按 B~H 段中的**相关层**逐条过，不必全跑——改 API 就看 B，改节点就看 C。
> **标注含义**：🔴 不满足即阻断合并；🟡 可合并但需在 PR 记录理由；💭 不阻塞。

---

## A. 通用自查（作者提 PR 前必过，12 条）

```markdown
- [ ] A1  改动能用一句话说清"改了什么、为什么"。说不清 → 说明还没想清，先别提交。
- [ ] A2  没有直接推到 master，分支名带类型前缀（feat/fix/perf/hotfix/docs/chore）。
- [ ] A3  本地 ruff check . 与 python -m compileall 通过。
- [ ] A4  新增的 except 分支写明了降级语义（跳过 / 返回空 / 终止），没有裸 except。
- [ ] A5  新增的外部调用（LLM/HTTP/DB/MinIO）设了超时，并说明了失败时的表现。
- [ ] A6  没有把密钥、内网地址、本机绝对路径写进代码或测试。
- [ ] A7  没有新增没用到的 import / 变量 / 函数（留给 ruff 也行，但别让它变多）。
- [ ] A8  改了行为，就同步改了 README 或 文档/ 下的对应描述。
- [ ] A9  改了检索、分块、schema、prompt，跑了 eval 或 12 条冒烟，并贴了结果。
- [ ] A10 PR 描述填了「影响面」和「回滚方式」。
- [ ] A11 diff 里没有顺手改的无关文件（格式化整文件、无关重命名会淹没真正的改动）。
- [ ] A12 自己先用审查者的眼光读一遍 diff（隔 20 分钟再读效果最好）。
```

## B. API 层（`api/*.py`）

**入参与校验**

- [ ] 🔴 每个入口都有边界校验：类型、空值、长度上限、枚举白名单（如 `content_type`）
- [ ] 🔴 文本入参有 `max_length`（`QueryRequest.query` 目前无上限，超长问题会直接进 LLM，既是成本也是注入面）
- [ ] 🟡 Pydantic 字段类型与默认值一致（`session_id: str = Field(None)` 应写 `str | None = Field(None)`）
- [ ] 🟡 路径参数/查询参数没有直接拿去拼文件路径（防目录穿越）

**错误与响应**

- [ ] 🔴 5xx 响应不把内部异常原文抛给调用方（`detail=f"query error: {e}"` 会泄漏栈信息与内部结构）；应记日志 + 返回通用文案
- [ ] 🔴 `raise HTTPException` 在 `except` 内要带 `from e`，保留因果链
- [ ] 🟡 对外字段只增不改；改名/删字段属破坏性变更，须版本化或双写过渡

**后台任务与 SSE**

- [ ] 🔴 长任务（分钟级）没有跑在同一进程的默认线程池里而不设上限——会挤占请求处理线程，且进程重启即丢任务。若暂不引入队列，至少限制并发数（如 `ThreadPoolExecutor(max_workers=4)`）并在文档里标注已知限制
- [ ] 🔴 共享的可变全局状态（SSE 队列表、事件 id 计数）有锁保护，或明确说明"只在单线程内访问"
- [ ] 🟡 后台任务里的异常不会静默消失：必须落 `logger.exception` + 终态标记
- [ ] 🟡 流式生成器的 `except Exception: return` 必须记日志，否则前端只会看到"卡住"
- [ ] 🟡 会话资源有回收路径（队列、重放缓冲、定时器），长期运行不随会话数增长

**CORS / 鉴权**

- [ ] 🔴 若服务可能绑定 `0.0.0.0` 或部署到内网/公网：`allow_origins=["*"]` + 无鉴权 = 任何人可读任意 `session_id` 的聊天历史、删历史、上传文件。当前仅监听 `127.0.0.1`，属于"可接受但必须写明前提"的状态——上线前必须换成白名单 + 鉴权
- [ ] 🟡 `/history/{session_id}` 类接口至少校验 session 归属（当前任何人拿到 id 即可读）

## C. LangGraph 节点层（`processor/*/nodes/*.py`）

**state 契约（本项目最容易出事的地方）**

- [ ] 🔴 节点返回的键，下游确实在读（新增 `xxx_hits` 却没进 `main_graph` 或下游节点 → 静默丢整条通道）
- [ ] 🔴 新增 state 字段时，同步更新 `state.py` 的默认值与注释；不要靠 `.get()` 兜底猜测
- [ ] 🔴 节点不再写某个键时，确认没有下游还在读它（`.get()` 返回 None 不会报错，只会静默降级）
- [ ] 🟡 一个节点只承担一类职责；`step_*` 拆分保持"入参校验 → 业务 → 组装"的顺序

**失败语义**

- [ ] 🔴 每个节点的失败行为与降级矩阵（PRD 3.8）一致：Milvus 挂 → 明确报错；LLM 挂 → 模板化 + `degraded=True`；Reranker 挂 → 用 RRF 序
- [ ] 🔴 不允许"失败即空列表"冒充"确实没检索到"——这两种情况对用户的语义完全不同（前者应说"服务异常"，后者才说"未找到"）
- [ ] 🟡 实体级失败（单题解析失败）必须计入 `parse_failed_entities` 并回传任务状态，不能只 `logger.error`
- [ ] 🟡 返回 `Optional` 的函数在 docstring 写明 None 的语义（`(emb, error)` / `None` 混用容易踩）

**性能**

- [ ] 🟡 循环内不重复做昂贵操作：同一查询的向量只编码一次（现有实现已在 `step_2_encode_query` 里做对，新代码不要破坏）
- [ ] 🟡 批量写库不用"逐条 query + 逐条 insert"（见 D 段 N+1）
- [ ] 💭 魔法数字提为模块级常量（`TOP_K_PER_COLLECTION`、`K=60` 已经是好例子，新代码沿用）

**可读性**

- [ ] 🟡 节点的入口函数保持"步骤调用 + 返回 dict"的形状，业务细节下沉到 `step_*`（现有风格很好，保持一致）
- [ ] 🟡 复杂正则/分块规则旁必须有"为什么这么写"的注释（例：`_strip_chapter_number` 用"数字>99 / 后接量词"防误伤——这类注释价值极高）
- [ ] 💭 日志里带可追踪的标识（`task_id` / `session_id`），便于串起一条链路

## D. 数据层（`utils/clients/`、`node_import_milvus.py`）

**幂等与数据完整性**

- [ ] 🔴 幂等 upsert 不是"先删后插"：删除成功/插入失败之间没有事务，会丢数据。用 `client.upsert()` 或"先插后删"
- [ ] 🔴 幂等键稳定且唯一；改幂等键等于改数据语义，必须走 L3
- [ ] 🔴 截断/跳过必须可观测：`_clip_varchar` 这类截断要汇总到任务结果（当前只 `logger.warning`，等于静默丢信息）
- [ ] 🟡 不要就地修改入参 dict（`_clip_varchar` 修改了 `row`；若调用方复用 record 会被污染）

**Milvus 具体坑**

- [ ] 🔴 `VARCHAR.max_length` 是按 **UTF-8 字节** 计，中文约 3 字节/字——按字符数配长度必然踩坑（现有 16384 的注释就是事故留下的，新字段照抄这个习惯）
- [ ] 🔴 搜索的 `metric_type` 必须与建索引时一致（建库 IP，检索却写 COSINE → 报错或被拒）。`utils/clients/milvus_utils.py` 里的 `create_hybrid_search_requests` 默认 COSINE，属历史遗留，**不要复制**
- [ ] 🔴 过滤表达式禁止直接拼用户输入：`f'bank_name like "%{name}%"'` 遇到引号会破坏表达式，甚至拼出恒真条件。至少做引号转义 + 长度限制
- [ ] 🟡 `output_fields` 要覆盖下游真正读取的字段（`_format_record` 读了 `learning_goal` / `description`，但 `_OUTPUT_FIELDS` 没返回 → 语义通道这些字段恒为 None）
- [ ] 🟡 批量操作避免 N+1：`for record: query + delete + insert` 在 1,752 题上是数千次往返

**Mongo / MinIO**

- [ ] 🟡 查询带 `limit`，写入有超时
- [ ] 🟡 对象名保留原文件名时要处理中文/空格（percent-encoding）与同名覆盖（现有 `__` 压平策略可参考）
- [ ] 🔴 解压/下载类操作有 zip-slip 与总量上限保护（已有 `zip_utils` 实现，新增入口不得绕过）

## E. LLM 与 Prompt 层（`common/prompt/`、`node_intent_route.py`、`node_answer_output.py`）

- [ ] 🔴 **prompt 与代码兜底逻辑必须一致**：prompt 说"输出 4 类意图"，代码就不能只处理 3 类（历史上真实出过偏差，见 commit `eecda61`）
- [ ] 🔴 结构化输出（JSON）必须容错解析：模型可能返回 ```json 包裹、前后带解释、字段缺失。解析失败要有兜底路径，不能直接抛
- [ ] 🔴 LLM 输出直接进答案/前端时，视为不可信输入（XSS、Markdown 注入）
- [ ] 🟡 prompt 改动的 PR 必须贴改前/改后的实际输出对比（至少 3 条典型问题）
- [ ] 🟡 涉及成本/延迟的开关（`ENABLE_HYDE` 这类）必须支持环境变量控制，并在注释里写清默认值与 A/B 结论
- [ ] 🟡 降级话术不能让用户误以为是"知识库没有"——服务异常要说服务异常
- [ ] 💭 温度、max_tokens、超时等参数集中配置，不散落在调用点

## F. 前端（`page/*.html`）

- [ ] 🔴 渲染 LLM 答案或文档内容时，不用 `innerHTML` 直插（除非经过 sanitize）。答案里可能带 `<script>`、`<img onerror=...>`
- [ ] 🔴 图片 URL 只接受 `http(s)` 且限定来源域（现有 `_is_image_url` 做了后缀校验，前端不要再放宽）
- [ ] 🟡 SSE 断线有重连与 `Last-Event-ID` 处理；重连失败给用户明确提示，不要静默重试到天荒地老
- [ ] 🟡 长任务（导入）轮询有上限与退避，页面关闭能停
- [ ] 💭 无障碍性明显问题（按钮可键盘触发、错误信息可读）

## G. 测试与评估

- [ ] 🔴 修 bug 必须带一条能复现该 bug 的用例（改前红、改后绿）
- [ ] 🔴 触碰检索/分块/意图路由：跑 `test/test_query_graph.py`（12 条）+ 必要时 `eval/run_retrieval.py`，贴 Hit@5 / MRR 对照

- [ ] 🟡 新增用例不得依赖本机绝对路径 / 外接盘 / 真实 Milvus：用 `tmp_path`、fixture、mock（现有 `test/*.py` 全部硬编码 `/Users/zdy/...`，是首要整改项）
- [ ] 🟡 断言要断言行为，不只断言"没抛异常"
- [ ] 💭 用例命名能说明场景（`test_zip_import_中文文件名应正常解压`）

## 附：审查者的 15 分钟读 diff 顺序

1. **先读 PR 描述**（30 秒）。说不清改什么的，直接打回让作者补——这不是刁难，是 PR 描述的缺失会让审查效率降到十分之一。
2. **看 diff 的文件清单**（30 秒）。有没有不该动的文件？有没有 `state.py` / `main_graph.py` / `schema` / `prompt` 这类 owner 路径？
3. **先看"错误路径"**（5 分钟）。`except` 分支、降级、`return None`、空列表——缺陷八成藏在这里，而不是 happy path。
4. **再看数据流**（5 分钟）。这个函数返回的东西，下游谁在用？有没有人还在读被删掉的键？
5. **最后看命名与风格**（2 分钟）。能用工具解决的，提一句"跑一下 ruff"就够，别开讨论会。
6. **写结论**（2 分钟）。先一句总评（能不能合、最大的风险是什么），再列 🔴/🟡/💭。

> 如果 15 分钟看不完，说明 PR 太大了——这本身就该打回拆分。
